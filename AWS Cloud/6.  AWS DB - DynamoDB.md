

# 🚀 1. What is DynamoDB?

### ✅ Interview Definition (Use this!)

> **Amazon DynamoDB is a fully managed, serverless NoSQL (non-relational) database service that provides single-digit millisecond performance at any scale.**


“DynamoDB is called a key-value database because data is accessed using a primary key, where the key uniquely identifies an item. The value is the entire item, which can be a structured JSON document, making it both a key-value and document database.”

## ✔️ Key Features

- Fully managed (no servers)
- Serverless (auto scaling)
- High availability (Multi-AZ)
- Key-value + document database
- Single-digit millisecond latency
- DynamoDB is **faster for key-based access patterns**
- RDS can be better for:
    - complex queries
    - joins
    - transactions


💡 Interview-safe answer:

> “DynamoDB provides predictable low latency for simple access patterns, while RDS is better for relational queries.”

### DynamoDB Storage Architecture

👉 A **partition = physical storage unit**
1. Take **Partition Key**
2. Apply **hash function**
3. Assign to partition

👉 Partitions are stored on **nodes (servers)**
✔️ Each node can hold multiple partitions

👉 Each partition has a **leader** Node (Write Node)
✔️ Handles:
- All **write operations**
- Strongly consistent reads

👉 Each partition is replicated to multiple nodes.
✔️ Located in different AZs
✔️ Handle:
- Eventually consistent reads

### Write Flow
```
1. Client sends write request
2. Request routed to partition
3. Leader node writes data
4. Data replicated to replicas
5. Write acknowledged
```

### Read Flow

##### ✅ Strongly Consistent Read
- Reads from leader
- Always latest data
##### ⚡ Eventually Consistent Read
- Reads from replica
- May return slightly stale data


“DynamoDB uses a distributed storage architecture where data is partitioned using a hash of the partition key and stored across multiple nodes. Each partition has a leader node that handles writes and replication to replica nodes across multiple availability zones. This enables high availability, fault tolerance, and supports both strongly consistent and eventually consistent reads.”

How data is being read - from leader or replica node?
You don’t directly know or control whether a read comes from a leader or replica node. Instead, you choose the read consistency level, and DynamoDB decides internally.


# 🧠 1. DynamoDB Read Consistency — Correct Concepts

DynamoDB supports **3 types of read behavior**:

```text
1. Eventually Consistent Read (default)
2. Strongly Consistent Read
3. Transactional Read
```


# ⚡ 2. Eventually Consistent Read (Default)

```text
ConsistentRead = false
```

### ✔️ Behavior

- May return **slightly stale data**
- Faster
- Cheaper (uses fewer RCUs)

### 🔍 Internally

```text
Client → DynamoDB → (Leader OR Replica)
```

✔️ Usually served from replicas  
✔️ But AWS decides (not guaranteed)

# 🔒 3. Strongly Consistent Read

```text
ConsistentRead = true
```

### ✔️ Behavior

- Always returns **latest data**
- Higher cost
- Slightly slower

### 🔍 Internally

```text
Client → DynamoDB → Leader (latest data)
```

# 🚀 4. Transactional Read 

```text
TransactGetItems
```

👉 Transactional read is:

> **Reading multiple items with ACID guarantees (consistent snapshot)**


### ✔️ Behavior

- Reads multiple item
- Ensures:
    - No partial updates
    - All data from same state

### 🔍 Internally

```text
Client → DynamoDB → Coordinated read across partitions
```

✔️ Not about leader vs replica  
✔️ About **consistency across items**


# ⚠️ 5. Key Differences (VERY IMPORTANT)

|Feature|Eventually Consistent|Strongly Consistent|Transactional|
|---|---|---|---|
|Latest data|❌ Not guaranteed|✅ Yes|✅ Yes|
|Scope|Single item/query|Single item/query|Multiple items|
|Cost|Low|Medium|High|
|Use case|High performance|Accurate reads|Financial consistency|



### ✅ Fixed Version

```text
ConsistentRead = false → Eventually consistent (default)
   → May read from replica or leader

ConsistentRead = true → Strongly consistent
   → Returns latest data (leader-based internally)

Transactional Read (TransactGetItems)
   → Reads multiple items with ACID guarantees
   → NOT about leader vs replica
```

# 💡 7. Important Insight (Interview Gold ⭐)

👉 Think like this:

```text
Eventually → Fast but may be stale
Strong     → Latest single item
Transactional → Consistent snapshot across multiple items
```


# 🎯 8. Interview Answer (Perfect)

> “DynamoDB supports eventually consistent reads by default, which may return stale data but are faster and cheaper. Strongly consistent reads ensure the latest data for a single item. Transactional reads, using TransactGetItems, provide ACID guarantees across multiple items, ensuring a consistent snapshot without partial updates.”


# Transaction Read example

## Items:

Order → status = PLACED  
Inventory → stock = 10


## Update happening:

Order → CONFIRMED  
Inventory → stock = 9


## ❌ Without Transaction

Order → CONFIRMED  
Inventory → 10

👉 ❗ Wrong (inventory not updated yet)


## ✅ With Transactional Read

Order → CONFIRMED

✔️ Consistent view

# 🧠 DynamoDB Write Consistency — Quick Summary

---

# 🚀 1. Types of Writes in DynamoDB

1. Normal Write (Standard Write)  
2. Transactional Write

---

# ⚡ 2. Normal Write (Standard)

### APIs:

- `PutItem`
- `UpdateItem`
- `DeleteItem`

---

## ✔️ Behavior

- Writes **one item at a time**
- Atomic at **single item level**
- No guarantee across multiple items

---

## ❌ Limitation

- Can lead to **partial updates**

---

## 💡 Example

Step 1: Deduct ₹1000 from A ✅  
Step 2: Add ₹1000 to B ❌ (failed)

👉 Result:

A = 2000  
B = 5000

❗ Inconsistent state

---

## ✔️ Use Cases

- Logs
- Social media posts
- Non-critical updates

---

# 🔒 3. Transactional Write

### API:

- `TransactWriteItems`

---

## ✔️ Behavior

- Writes **multiple items**
- ACID guarantees:
    - Atomicity
    - Consistency
    - Isolation

---

## ✅ Guarantee

Either ALL operations succeed OR NONE

---

## 💡 Example

Transfer ₹1000 from A → B

---

### Result:

A = 2000  
B = 6000

✔️ OR

A = 3000  
B = 5000

✔️ No partial updates ❗

---

## ✔️ Use Cases

- Banking 💰
- Payments
- Order + inventory systems

---

# ⚖️ 4. Key Differences

|Feature|Normal Write|Transactional Write|
|---|---|---|
|Scope|Single item|Multiple items|
|Atomicity|Item-level|Multi-item (ACID)|
|Consistency|Limited|Strong|
|Cost|Lower|Higher (~2x)|
|Complexity|Simple|Higher|

---

# 💰 5. Cost Insight

Transactional Write ≈ 2x cost of normal write

👉 Because:

- Coordination across items
- Validation + locking

---

# 🎯 6. Interview Answer (Perfect)

> “In DynamoDB, normal writes operate at the individual item level and are atomic only for that item. Transactional writes, using TransactWriteItems, provide ACID guarantees across multiple items, ensuring that either all operations succeed or none do, which is critical for use cases like financial transactions.”

---

# 🧠 7. Final Mental Model

Normal Write        → single item, fast  
Transactional Write → multi-item, safe (ACID)


# ⚠️ Exam Tips

✔️ Normal write = item-level atomic  
✔️ Transaction = multi-item atomic  
✔️ Transaction = expensive but safe


# 🚀 1. What is RCU?

> **RCU (Read Capacity Unit) defines how many read operations your DynamoDB table can handle per second.**

---

# 📊 2. What Determines RCU?

👉 3 key factors:

1. Item Size (KB)  
2. Read Requests per second  
3. Read Consistency type

# 📦 3. Item Size Rule (VERY IMPORTANT)

👉 DynamoDB reads data in:

Blocks of 4 KB

## ✔️ Rounding Rule

|Actual Size|Billed Size|
|---|---|
|2 KB|4 KB|
|6 KB|8 KB|
|10 KB|12 KB|
# ⚡ 4. RCU Based on Consistency

---

## 🔒 Strongly Consistent Read

1 RCU = 1 read/sec for 4 KB

---

## ⚡ Eventually Consistent Read

1 RCU = 2 reads/sec for 4 KB

✔️ Costs 50% of strong

---

## 🚀 Transactional Read

1 read = 2 RCUs (for 4 KB)

✔️ Costs 2x of strong

---

# 🧮 5. RCU Formula

RCU = (Item Size / 4 KB) × Reads per second × Consistency factor

---

## Consistency Factor

|Type|Factor|
|---|---|
|Strong|1|
|Eventual|0.5|
|Transactional|2|

---

# 💡 6. Examples

---

## ✅ Example 1 (Strong Read)

Item size = 4 KB  
Reads/sec = 100  
  
RCU = (4/4) × 100 × 1 = 100 RCU

---

## ✅ Example 2 (Item = 6 KB → rounded to 8 KB)

RCU = (8/4) × 50 × 1 = 2 × 50 = 100 RCU

---

## ✅ Example 3 (Eventually Consistent)

Item = 4 KB  
Reads/sec = 100  
  
RCU = (4/4) × 100 × 0.5 = 50 RCU

---

## ✅ Example 4 (Transactional)

Item = 4 KB  
Reads/sec = 100  
  
RCU = (4/4) × 100 × 2 = 200 RCU

---
“RCU in DynamoDB defines the number of read operations per second a table can handle. One RCU supports one strongly consistent read per second for up to 4 KB of data. Eventually consistent reads consume half the RCU, while transactional reads consume double. The total RCU depends on item size, read frequency, and consistency model.”

# 🚀 1. What is WCU?

> **WCU (Write Capacity Unit) defines how many write operations your DynamoDB table can handle per second.**

---

# 📊 2. What Determines WCU?

1. Item size (KB)  
2. Writes per second  
3. Write type (Standard vs Transactional)

---

# 📦 3. Item Size Rule (VERY IMPORTANT)

👉 DynamoDB writes are calculated in:

Blocks of 1 KB

---

## ✔️ Rounding Rule

|Actual Size|Billed Size|
|---|---|
|0.5 KB|1 KB|
|1.5 KB|2 KB|
|2.2 KB|3 KB|

---

# ⚡ 4. Types of Writes

---

## ✅ Standard Write

### APIs:

- `PutItem`
- `UpdateItem`
- `DeleteItem`

---

### ✔️ Rule

1 WCU = 1 write/sec for 1 KB item

---

## 🚀 Transactional Write

### API:

- `TransactWriteItems`

---

### ✔️ Rule

1 write = 2 WCUs (for 1 KB)

✔️ 2x cost of standard

---

# 🧮 5. WCU Formula

WCU = (Item Size / 1 KB) × Writes per second × Write factor

---

## Write Factor

|Type|Factor|
|---|---|
|Standard|1|
|Transactional|2|

---

# 💡 6. Examples

---

## ✅ Example 1 (Standard)

Item size = 1 KB  
Writes/sec = 100  
  
WCU = (1/1) × 100 × 1 = 100 WCU

---

## ✅ Example 2 (1.5 KB → rounded to 2 KB)

Item size = 2 KB  
Writes/sec = 50  
  
WCU = (2/1) × 50 = 100 WCU

---

## ✅ Example 3 (Transactional)

Item size = 1 KB  
Writes/sec = 100  
  
WCU = (1/1) × 100 × 2 = 200 WCU

---

“WCU in DynamoDB represents the number of write operations a table can handle per second. One WCU allows writing 1 KB of data per second. If the item size exceeds 1 KB, it is rounded up. Transactional writes consume double the WCU compared to standard writes because of additional consistency guarantees.”


# 🧠 DynamoDB Capacity Modes

DynamoDB has **2 capacity modes**:

```text
1. Provisioned Capacity
2. On-Demand Capacity
```

---

# 🚀 1. Provisioned Capacity

> You **define RCU & WCU in advance**

## ✔️ How it works

```text
You set:
- Read Capacity (RCU)
- Write Capacity (WCU)
```

👉 Example:

- 100 RCU
    
- 50 WCU
    


## ✔️ Characteristics

- Fixed capacity
    
- Predictable workload
    
- Can enable **Auto Scaling**
    

---

## 💰 Cost

✔️ Cheaper (if workload is stable)


## ⚠️ Risk

❗ Under-provision → throttling  
❗ Over-provision → wasted money


## 🧠 Use Cases

- Banking systems
    
- Enterprise apps
    
- Predictable traffic
    

---

# ⚡ 2. On-Demand Capacity

> DynamoDB automatically handles scaling

---

## ✔️ How it works

```text
No capacity planning needed
Pay per request
```

---

## ✔️ Characteristics

- Auto scaling (instant)
    
- Handles unpredictable traffic
    
- No RCU/WCU setup
    

---

## 💰 Cost

✔️ More expensive per request

---

## 🧠 Use Cases

- Startups
    
- Unknown traffic
    
- Spiky workloads (flash sale, viral app)
    

---

# ⚖️ 3. Key Differences

|Feature|Provisioned|On-Demand|
|---|---|---|
|Capacity setup|Manual|Automatic|
|Scaling|Manual/Auto Scaling|Fully automatic|
|Cost|Lower (steady load)|Higher|
|Traffic type|Predictable|Unpredictable|
|Throttling risk|Yes|Very low|

---

# 🧠 4. Simple Analogy

```text
Provisioned → Book fixed seats in advance
On-Demand  → Pay per ride (Uber style)
```

---

# ⚠️ 5. Important Exam Points

✔️ You can switch between modes  
✔️ On-demand handles sudden spikes  
✔️ Provisioned needs planning  
✔️ Auto scaling helps in provisioned

---

# 🎯 6. Interview Answer (Perfect)

> “DynamoDB offers two capacity modes: provisioned and on-demand. In provisioned mode, you define read and write capacity units in advance, making it cost-effective for predictable workloads. In on-demand mode, DynamoDB automatically scales based on traffic, making it ideal for unpredictable workloads, though it is more expensive per request.”

---

# 🧱 1. DynamoDB Base Table

## 📌 Definition

A **DynamoDB table** stores data as **items (JSON documents)** and is designed for **highly scalable, low-latency access**.

---

## 🔑 Primary Key (MANDATORY)

Every table must have a primary key:

### 🔹 Option 1: Partition Key (PK only)

```plaintext
PK: CustomerID
```

- Uniquely identifies item
    
- Used for direct lookup
    

---

### 🔹 Option 2: Composite Key (PK + Sort Key)

```plaintext
PK: CustomerID
SK: OrderID
```

✔️ Most common design

---

## 🧠 How Data is Stored

- Partition Key → hashed → routed to **SSD-backed partition**
    
- Within partition → sorted by **Sort Key**
    

```plaintext
Partition: CustomerID = C1
--------------------------------
OrderID: O1
OrderID: O2
OrderID: O3
```

---

## 📦 Example Base Table

```json
{
  "CustomerID": "C1",
  "OrderID": "O1",
  "InvoiceID": "INV-100",
  "Status": "SHIPPED",
  "Date": "2025-01-01",
  "address": "123 Street",
  "city": "NY",
  "zipCode": "10001"
}
```

---

# 🔍 2. Secondary Indexes Overview

👉 DynamoDB supports:

1. **Local Secondary Index (LSI)**
    
2. **Global Secondary Index (GSI)**
    

✔️ Used to support **different query patterns**

---

# 🔍 3. Local Secondary Index (LSI)

---

## 📌 Definition

- Same **Partition Key as base table**
    
- Different **Sort Key**
    

👉 From your notes:  
LSI enables new query patterns within the same partition

---

## 🔑 Key Structure

```plaintext
Base Table:
PK: CustomerID
SK: OrderID

LSI:
PK: CustomerID        (same)
SK: InvoiceID         (new)
```

---

## 🧠 Storage Behavior

✔️ Stored **alongside base table**  
✔️ Same physical partition (same SSD)  
✔️ No full duplication  
✔️ Shares throughput

---

## 🔎 What Fields Can Be Used?

### ✔️ Allowed:

- Sort key = **any attribute present in base table**
    
    - Example: `InvoiceID`, `Date`, `Amount`
        

### ❗ Rule:

- Attribute **must exist in items**
    

---

## 📊 Query Capability

You can query:

```plaintext
CustomerID = C1
Sort by InvoiceID
```

---

## 📦 Attribute Projection

From your document:

- ALL → full item
    
- KEYS_ONLY → only keys
    
- INCLUDE → selected attributes
    

---

## ✅ Advantages

- Strong consistency supported
    
- No extra storage duplication
    
- Efficient for same-partition queries
    

---

## ❌ Limitations

- Must be created at table creation
    
- Max **5 LSIs**
    
- **10GB per partition limit**
    
- Shared throughput
    

---

# 🌐 4. Global Secondary Index (GSI)

---

## 📌 Definition

- Different **Partition Key**
    
- Optional **Sort Key**
    
- Enables **completely new access patterns**
    

👉 From your notes:  
GSI allows querying using non-primary key attributes

---

## 🔑 Key Structure

```plaintext
Base Table:
PK: CustomerID
SK: OrderID

GSI:
PK: InvoiceID        (new)
SK: StatusDate       (optional)
```

---

## 🧠 Storage Behavior

✔️ Stored in **separate partitions**  
✔️ Acts like **separate table internally**  
✔️ Data is **copied (projected)**  
✔️ Async replication → eventual consistency

---

## 🔎 What Fields Can Be Used?

### ✔️ Allowed:

- Any attribute in base table:
    
    - `InvoiceID`
        
    - `Status`
        
    - `Date`
        
    - `city`
        

### ❗ Important Rules:

1. Attribute must exist in item
    
2. If attribute missing → item NOT in GSI (**sparse index**)
    

---

## 📊 Example

```plaintext
GSI:
PK: Status
SK: Date
```

Query:

```plaintext
Find all SHIPPED orders sorted by Date
```

---

## 📦 Attribute Projection

- ALL
    
- KEYS_ONLY
    
- INCLUDE
    

---

## ✅ Advantages

- New query patterns
    
- Independent scaling
    
- Can be added anytime
    

---

## ❌ Limitations

- Extra storage cost (data duplication)
    
- Eventual consistency
    
- Separate capacity management
    

---

# ⚔️ 5. LSI vs GSI (Must Memorize)

|Feature|LSI|GSI|
|---|---|---|
|Partition Key|Same|Different|
|Sort Key|Different|Optional|
|Storage|Same partition|Separate storage|
|Data Copy|Minimal|Yes|
|Consistency|Strong + Eventual|Eventual only|
|Creation Time|At table creation|Anytime|
|Throughput|Shared|Separate|
|Limit|5|Many|

---

# 🧠 6. What Fields Can You Choose? (CRITICAL SECTION)

---

## ✔️ For LSI

- Must use:
    
    - Same **Partition Key**
        
- Can choose:
    
    - Any **existing attribute as Sort Key**
        

```plaintext
Valid:
PK: CustomerID
SK: Date / InvoiceID / Amount
```

---

## ✔️ For GSI

- Can define:
    
    - New PK from any attribute
        
    - Optional SK from any attribute
        

```plaintext
Valid:
PK: Status
SK: Date
```

---

## ❌ Invalid Cases

|Scenario|Allowed?|
|---|---|
|Attribute not present in items|❌ No|
|New computed field without storing|❌ No|
|Missing attribute in some items|✔️ (sparse index)|

---

# 🔥 7. Query Behavior (VERY IMPORTANT)

---

## Base Table Query

```plaintext
TableName: Orders
Key: CustomerID
```

---

## GSI Query

```plaintext
TableName: Orders
IndexName: InvoiceIndex
```

👉 Same table name, different index

---

# 🧠 8. Final Mental Model

---

### LSI

```plaintext
Same Partition → Different Sorting
```

---

### GSI

```plaintext
New Partition → New Access Pattern
```

❗ “Can GSI use attribute not in table?” → NO  
❗ “Does GSI create new table?” → Internally yes, logically no  
❗ “Can LSI be added later?” → NO  
❗ “Does GSI support strong consistency?” → NO

# 🚀 10. Design Thinking (MOST IMPORTANT)

👉 Always design based on:

```plaintext
ACCESS PATTERNS
```

Ask:

- How will I query data?
    
- What is my partition key?
    
- Do I need new access pattern?
    

---

# 🧠 Golden Rules

✔️ Base table → main query  
✔️ LSI → alternate sorting (same PK)  
✔️ GSI → new query dimension

---


# 🧠 Storage Summary (Most Important)

### 🔹 LSI

- Same partition
    
- Same SSD
    
- No full duplication
    
- Alternate **sorted view**
    

---

### 🔹 GSI

- Separate partitions
    
- Separate SSD
    
- Data is **replicated**
    
- Acts like **new table**
    

---

# ❓ Can We Use LSI and GSI Together?

✔️ **YES — very common design**

---

## 💡 Example

```plaintext
Table:
PK: CustomerID
SK: OrderID

LSI:
- InvoiceID (same PK, different sorting)

GSI:
- InvoiceID (new PK)
- Status + Date
```

---

- Separate storage
    
- Data copied asynchronously
    
- Eventually consistent

### DynamoDB Architecture:

```
Client → API → DynamoDB
             ↓
       Partition Layer
             ↓
      Storage Nodes (SSD)
             ↓
     Replication (Multi-AZ)
```

# 🌐 1. Client → API

### What happens here?

👉 The **client (app / browser / backend)** sends a request:

- PutItem (write)
- GetItem / Query (read)

```
PutItem → Orders table
userId = 101
orderId = ord_1
```

### API Layer (DynamoDB Service Endpoint)

👉 This is the **managed AWS API endpoint**
✔️ Handles:
- Authentication (IAM)
- Request validation
- Routing decision

💡 Think:
> “Front door of DynamoDB”


# ⚙️ 2. Partition Layer (MOST IMPORTANT)

👉 This is where DynamoDB decides:

> “Where should this data live?”

---

## 🔑 How?

- Takes **Partition Key**
- Applies **hash function**
- Maps to a **partition**
```
userId = 101 → Hash → Partition A
userId = 202 → Hash → Partition B
```

## 🧠 Why this matters?

✔️ Enables horizontal scaling  
✔️ Distributes load evenly

# 💾 3. Storage Nodes (SSD)

Once partition is selected:

👉 Data is stored in **storage nodes**

## What are these?

- Physical machines (managed by AWS)
- Backed by **SSD (Solid State Drives)**

## Why SSD?

✔️ Very fast reads/writes  
✔️ Low latency (milliseconds)

## What is stored?

- Your item (JSON-like data)
- Index data (GSI/LSI)

# 🔁 4. Replication (Multi-AZ)

👉 After writing to storage:

DynamoDB automatically:

> Replicates data across multiple Availability Zones

## Example

Write happens →  
   AZ-1 (primary)  
   AZ-2 (replica)  
   AZ-3 (replica)

## Why?

✔️ High availability (99.999%)  
✔️ Fault tolerance  
✔️ No data loss (durability)


### 🔄 Full Write Flow (Putting It Together)

```
1. Client sends PutItem
2. API authenticates request
3. Partition layer hashes key → finds partition
4. Data written to SSD node
5. Replicated across multiple AZs
6. Success response returned
```

### 🔍 Full Read Flow
```
1. Client sends Query/GetItem
2. API validates request
3. Partition layer finds partition
4. Reads from SSD (or replica)
5. Returns result in milliseconds
```
### ⚡ Why DynamoDB is So Fast

✔️ Direct partition lookup (no scanning)  
✔️ SSD storage  
✔️ Distributed system  
✔️ No joins


### Important
“When a request is sent to DynamoDB, it first goes through the API layer for authentication and validation. Then DynamoDB uses the partition key to hash and route the request to a specific partition. The data is stored on SSD-backed storage nodes, and it is automatically replicated across multiple availability zones for high availability and durability.”
