# 💡 What is Serverless (in simple terms)

**Serverless = You don’t manage servers. AWS does.**

- Servers still exist ❗
- But:
    - No provisioning
    - No scaling setup
    - No patching
    - No capacity planning

👉 You just **run code or use services on demand**

# ⚡ Core Idea

```
Need compute? → AWS gives instantly
Done?          → AWS takes it back
Pay?           → Only for usage
```


# 🧠 Key Characteristics

- **No infrastructure management**
- **Automatic scaling (0 → millions)**
- **Pay-per-use (no idle cost)**
- **Built-in high availability**
- **Event-driven**
- **Stateless & short-lived execution**

# 🧠 What is API Gateway?


**Amazon API Gateway** is a **fully managed AWS service** that lets you:

> **Create, publish, secure, monitor, and scale APIs** that act as a front door to your backend systems.


Because it:

- Receives requests from clients
- Routes them to the correct backend
- Applies security, throttling, validation
- Returns responses back to clients

# 📘 AWS API Gateway – Endpoint Types Documentation

## 🔰 1. Introduction

When creating an API Gateway REST API in AWS, you must choose an **Endpoint Type**.

👉 This decision is important because it defines:

- How clients access your API
    
- How AWS routes requests internally
    

There are **3 types of endpoints**:

1. Regional
    
2. Edge-Optimized
    
3. Private
    

---

# 🌍 2. Regional Endpoint

## 💡 Concept (Simple Words)

Your API is deployed in **one AWS region**, and users directly connect to that region over the internet.

👉 Example:  
If your API is in **Mumbai (ap-south-1)**, every user request goes to Mumbai.

---

## 🔄 Flow Diagram

```
Client → Internet → API Gateway (Mumbai Region) → Backend (Lambda / EC2)
```

---

## ⚙️ How It Works

- API is hosted in a **specific AWS region**
    
- No CDN involved
    
- Direct communication between client and API
    

---

## ✅ When to Use

- Users are **close to your AWS region**
    
- Applications targeting **specific geography**
    
- Need **low latency within same region**
    

👉 Example:

- India-based application with Indian users
    

---

## ❌ Limitations

- High latency for **international users**
    
- Performance drops for distant clients
    

---

# 🌐 3. Edge-Optimized Endpoint (Global API)

## 💡 Concept (Simple Words)

AWS uses **CloudFront (CDN)** to bring your API closer to users worldwide.

👉 Users connect to the **nearest CloudFront location**, not directly to your region.

---

## 🔄 Flow Diagram

```
Global Client → Nearest CloudFront Edge → API Gateway (Mumbai) → Backend
```

---

## ⚙️ How It Works

- API is still in one region (e.g., Mumbai)
    
- CloudFront acts as a **global entry point**
    
- Requests are routed efficiently to backend
    

---

## ✅ When to Use

- Global users 🌍
    
- Mobile apps used across countries
    
- Need **low latency worldwide**
    

👉 Example:

- SaaS product with users in US, Europe, India
    

---

## ❌ Limitations

- Slightly **higher cost** (CloudFront involved)
    
- **Deployment slower** due to CDN propagation
    

---

# 🔒 4. Private Endpoint (VPC Only)

## 💡 Concept (Simple Words)

This API is **NOT available on the internet**.  
It is only accessible **inside your AWS VPC**.

---

## 🔄 Flow Diagram

```
EC2 / Lambda / ECS (VPC)
        ↓
VPC Interface Endpoint
        ↓
API Gateway (Private)
```

---

## ⚙️ How It Works

- Uses **VPC Endpoint (Interface Endpoint)**
    
- No public internet exposure
    
- Fully private communication
    

---

## ✅ When to Use

- Internal company APIs 🏢
    
- Secure backend systems
    
- No internet access allowed
    

👉 Example:

- Microservices communication inside VPC
    

---

## ❌ Limitations

- Must create **VPC Endpoint**
    
- Not accessible publicly
    

---

# 🔐 AWS API Gateway – Endpoint Security Policy (TLS)

## 🔰 1. What is TLS?

**TLS (Transport Layer Security)** is a protocol that protects communication between:

- Client (browser / mobile app)
- API Gateway

👉 Think of TLS as a **secure tunnel** between client and API.


## 🔒 What TLS Ensures

- ✅ Data is **encrypted**
- ✅ Attackers **cannot read data**
- ✅ Prevents **Man-in-the-Middle attacks**
- ✅ Confirms client is talking to the **real API server**


## 🔄 Simple Flow

```id="tlsflow1"
Client → 🔐 Encrypted TLS Connection → API Gateway → Backend
```

# ⚙️ 2. What is API Endpoint Security Policy?

When creating a REST API, AWS asks:

👉 **“Which TLS Security Policy do you want?”**

This policy controls:

- Minimum TLS version allowed
- Cipher suites (encryption algorithms)
- Whether **FIPS mode** is required

📌 Important:

- This applies to **default API Gateway invoke URL**
- No custom domain required


# 🔑 3. TLS Versions (Policy Options)

## 🟢 TLS 1.2 (Standard ✔️)

- Strong encryption
- Supported by all modern apps
- Most commonly used today

👉 **Best default choice**


## 🚀 TLS 1.3 (Newest & Fastest)

- Released in 2018
- More secure than TLS 1.2
- Faster handshake → better performance

👉 Ideal for **modern, high-performance APIs**


# 🛡️ 4. Advanced Security Concepts

## 🏛️ FIPS (Compliance Security)

- Stands for **Federal Information Processing Standards**
- Uses **government-approved encryption**

👉 Required in:

- Government
- Banking
- Healthcare
- Defense systems


## 🔄 PFS (Perfect Forward Secrecy)

- Generates **new encryption key for every session**


👉 Benefit:

- Even if one key is compromised → past data remains safe


## 🔮 PQ (Post-Quantum Cryptography)

- Future-proof encryption
- Resistant to **quantum computer attacks**

👉 Still emerging but important for long-term security


# 🔄 5. Where This Policy Applies

From the diagram (page 1):

👉 Security policy applies to:

```id="applyflow"
Client → TLS Policy → API Gateway Default URL
```

---

## 📌 Important Notes

- ✔️ Applies only to **default invoke URL**
- ✔️ Custom domain can have **different security policy**
- ✔️ Custom domains allow:
    
    - SSL certificates
    - mTLS (mutual TLS)
    - Hostname validation

# 🔐 API Gateway – Access Mode (BASIC vs STRICT)

When you use **advanced security policies** (like TLS 1.3 or enhanced security), AWS asks you to choose:

👉 **API Access Mode**

- BASIC
- STRICT

# 🟢 1. BASIC Mode (Default)

## 💡 Simple Meaning

- Normal behaviour
- No extra security validation

## ⚙️ How it works

- API Gateway accepts requests if TLS connection is valid
- Does NOT perform deep checks

## ✅ Use Case

- General applications
- When you don’t need strict security

# 🔴 2. STRICT Mode (High Security)

## 💡 Simple Meaning

STRICT mode adds **extra security checks** before allowing requests.

👉 It protects against advanced attacks like **Domain Fronting**
## 🚨 What is Domain Fronting?

A trick where:
- TLS uses one domain
- HTTP request uses another domain
```id="df1"
TLS (SNI): api.mycompany.com  
HTTP Host: attacker.com  
```

👉 Connection succeeds but request is misused ❌

## 🛡️ What STRICT Mode Does

Before allowing request:

- ✔️ Verifies request comes from correct endpoint type
- ✔️ Matches TLS domain with HTTP host
- ✔️ Blocks suspicious traffic

👉 If anything mismatches → ❌ Request rejected

## 🔍 STRICT Mode Checks

### 1. Endpoint Type Validation

- Request must come from same endpoint type:
    
    - Regional
    - Edge-Optimized
    - Private

👉 Mismatch → Rejected

### 2. SNI vs Host Matching

- TLS domain must match HTTP host
```id="sni1"
SNI domain == Host domain → ✅ Allowed  
SNI domain ≠ Host domain → ❌ Rejected
```

### 3. CloudFront Protection (Edge APIs)

- Prevents domain fronting using CloudFront safeguards

# ⚖️ BASIC vs STRICT (Quick View)

|Feature|BASIC 🟢|STRICT 🔴|
|---|---|---|
|Security Level|Normal|High|
|Extra Validation|❌ No|✅ Yes|
|Domain Fronting Protection|❌ No|✅ Yes|
|Performance|Faster|Slightly strict checks|

# 🎯 Final Takeaway

- **BASIC** → Simple, default, less secure
- **STRICT** → Recommended for **production & secure APIs**

👉 If security matters (finance, auth APIs, enterprise systems):  
✔️ Always go with **STRICT mode**

# 📘 REST API – Resources & Methods

## 🔰 1. Basic Idea

In REST API (API Gateway):

👉 Everything is built using:

- **Resources** → URL paths
- **Methods** → Actions on those paths


## 🔄 Request Flow (Important)

From your diagram (page 1):

```text
Client → Resource → Method → Backend (Lambda / etc.)
```

👉 REST API gives full control:

- Validate request
- Transform data
- Control headers, query params, body

---

# 🌐 2. What is a Resource?

## 💡 Simple Meaning

A **Resource = URL path**

### Examples:

- `/users`
- `/orders`
- `/products`



## 🔹 Root Resource (/)

- Automatically created
- Cannot be deleted
- Starting point of API

```text
/
```

👉 Base URL:

```text
https://api-id.execute-api.region.amazonaws.com/stage/
```

## 🔹 Child Resources

Resources inside root:

```text
/
└── users
    └── {id}
```

### Examples:

- `/users` → Get all users
- `/users/{id}` → Get specific user

👉 URL:

```text
https://api-id.execute-api.region.amazonaws.com/stage/users
```

# ⚙️ 3. What is a Method?

## 💡 Simple Meaning

A **Method = HTTP action on a resource**

👉 Example:

```text
Resource: /users  
Methods: GET, POST
```

---

## 🔄 Structure

```text
/
└── users
    ├── GET
    └── POST
```

👉 Important Rule:  
❗ **No resource = No method**

---

# 🧪 4. Methods on Different Levels

## On Root Resource

```text
/
├── GET
└── POST
```

👉 URL:

```text
.../stage/
```

---

## On Child Resource

```text
/
└── users
    ├── GET
    └── POST
```

👉 URL:

```text
.../stage/users
```

---

# 🔧 5. What You Configure in a Method

From your diagram:

Each method controls everything 👇

- HTTP method type
- Integration (Lambda, EC2, etc.)
- Request validation
- Query parameters
- Headers
- Request body
- Proxy integration
👉 This is why REST API = **full control**

---

# 🔢 6. Supported HTTP Methods

|Method|Purpose|
|---|---|
|GET|Read data|
|POST|Create data|
|PUT|Update full|
|PATCH|Update partial|
|DELETE|Remove data|
|HEAD|Headers only|
|OPTIONS|CORS / preflight|
|ANY|Matches all methods|

---

## 💡 Special: ANY Method

```text
ANY → One method handles all HTTP requests
```

👉 Useful for:

- Proxy APIs
- Lambda proxy integrations
    

---

# ⚖️ 7. REST API vs HTTP API (Quick Insight)

From your document:

|HTTP API|REST API|
|---|---|
|Simple|Advanced|
|Just request/response|Full control|
|Less configuration|Detailed configuration|

---

# 🎯 Final Takeaway

- **Resource = Path (/users)**
    
- **Method = Action (GET, POST)**
    
- Methods are always inside resources
    
- REST API gives **fine-grained control over requests**




# 🔗 REST API – Integration Types

## 🔰 1. What is Integration?

💡 **Integration = Where your API sends the request after receiving it**

👉 Example:

```text
Client → GET /users → API Gateway → Integration → Backend
```

✔️ Integration decides **which backend handles the request**

---

# 🔄 2. Request Flow

```text
Client → API Gateway → Integration → Backend → Response → Client
```

---

# 🧩 3. Types of Integrations

AWS REST API supports **5 main integration types**:

---

## 🟢 1. Lambda Integration (Most Popular)

## 💡 Simple Meaning

API Gateway calls a **Lambda function**

```text
Client → API Gateway → Lambda → Response
```

## ✅ Use Case

- Serverless applications
    
- Event-driven systems
    

✔️ Fully managed, scalable

---

## 🌐 2. HTTP Integration

## 💡 Simple Meaning

API Gateway forwards request to a **public HTTP endpoint**

```text
Client → API Gateway → HTTP Backend (URL)
```

## ✅ Use Case

- Existing web apps
    
- External APIs
    

✔️ Simple **pass-through**

---

## 🧪 3. Mock Integration

## 💡 Simple Meaning

No backend is used

```text
Client → API Gateway → Mock Response
```

## ✅ Use Case

- Testing APIs
    
- Demos
    
- Prototyping
    

✔️ Returns fixed response

---

## 🔒 4. VPC Link Integration

## 💡 Simple Meaning

Connect API Gateway to **private resources inside VPC**

```text
Client → API Gateway → VPC Link → ALB/NLB → Private Service
```

## 🤔 Why Needed?

- API Gateway = Public
    
- Backend = Private
    

👉 VPC Link acts as **secure bridge**

## ✅ Use Case

- Private microservices
    
- Internal backend systems
    

✔️ No need to expose backend to internet

---

## ⚡ 5. AWS Service Integration

## 💡 Simple Meaning

API Gateway directly calls **AWS services (no Lambda)**

```text
Client → API Gateway → AWS Service (S3 / DynamoDB / SQS / etc.)
```

## ✅ Examples

- Store data in DynamoDB
    
- Send message to SQS
    
- Stream data to Kinesis
    

## ⚙️ Requirements

- IAM Role (API Gateway assumes it)
    
- Permissions
    
- Mapping templates
    

✔️ Powerful but slightly complex

---

# 🔁 REST API – Proxy Integration

## 🔰 1. What is Proxy Integration?

💡 **Proxy Integration = API Gateway forwards the entire request to backend WITHOUT changing anything**

👉 No:

- ❌ Filtering

- ❌ Transformation
    
- ❌ Extra configuration
    

✔️ Backend handles everything

---

## 🔄 Request Flow

```text
Client → API Gateway → Backend (Lambda / HTTP / VPC) → Response → Client
```

👉 API Gateway acts like a **pass-through**

---

# 🎯 2. Real-Life Analogy

From your diagram:

- API Gateway = 📦 **Courier boy**
    
- Backend = 🏢 **Office worker**
    

👉 Courier:

- Does NOT open package
    
- Does NOT modify anything
    
- Just delivers
    

👉 Backend:

- Opens request
    
- Processes it
    
- Sends response
    

✔️ That is Proxy Integration

---

# 📦 3. What Data is Forwarded?

When proxy is enabled, **everything is sent as-is**:

- HTTP Method (GET, POST, etc.)
    
- URL path (`/users`, `/login`)
    
- Query parameters (`?id=10`)
    
- Headers
    
- Request body (JSON, form data)
    

👉 Full request is forwarded

---

# 🔌 4. Supported Proxy Integrations

You can use proxy with:

- ✅ Lambda (Lambda Proxy Integration)
    
- ✅ HTTP / HTTPS backend
    
- ✅ VPC Link (private ALB/NLB)
    

---

# ✅ 5. When to ENABLE Proxy Integration

Use Proxy when:

- ✔️ You want **simple setup**
    
- ✔️ You want **fast development**
    
- ✔️ You want **full control in backend**
    
- ✔️ You are building **modern APIs**
    
- ✔️ You don’t want API Gateway complexity
    

---

# ❌ 6. When to DISABLE Proxy Integration

Avoid Proxy when:

- ❌ You want API Gateway to:
    
    - Modify request
        
    - Filter fields
        
    - Transform response
        
- ❌ You need **mapping templates**
    
- ❌ Working with **legacy systems**
    

👉 Example:

- Backend expects fixed format
    
- Client sends extra data → needs filtering
    

---

# ⚙️ 7. Proxy Integration Settings

## 🧱 1. Response Transfer Mode

### 🟢 Buffered (Default)

```text
Client → Request → Backend processes fully (Lambda) → API Gateway sends full response
```

✔️ Waits for complete response

### 🔵 Stream (Advanced)

```text
Client → Request → Backend sends chunks → Client receives continuously
```
✔️ Real-time streaming  
❗ Rarely used

## ⏱️ 2. Integration Timeout

💡 Maximum time API Gateway waits for backend response.

```text
If response < timeout → ✅ Success  
If response > timeout → ❌ 504 Error
```

# ⚖️ 8. Proxy vs Non-Proxy (Quick Comparison)

|Feature|Proxy Integration|Non-Proxy Integration|
|---|---|---|
|Request Handling|Full pass-through|Custom mapping|
|Complexity|Simple|Complex|
|Control Location|Backend|API Gateway|
|Use Case|Modern apps|Legacy / transformation|

---

# 🎯 Final Takeaway

👉 Proxy Integration =

```text
"API Gateway forwards everything → Backend handles everything"
```

✔️ Best for:

- Serverless (Lambda proxy)
- Microservices
- Fast development

❗ Not ideal when you need request/response transformation

# 💡 Architect Tip

✔️ Use **Lambda Proxy Integration** for most modern apps  
✔️ Combine with:

- API Gateway Authorizers
- Validation (if needed)
- Logging (CloudWatch)

# 🧠 API Gateway Resource Policy 

👉 A **resource policy** is an **extra security layer** applied directly to your API Gateway.

Think of it like:

```text
Gate before authentication
```


# 🔐 What It Does

It controls **who can even reach your API**, based on:

- IP address
- AWS account
- IAM principal
- VPC endpoint (for private APIs)
- AWS Organization

# ⚙️ Key Behavior (Very Important ❗)

```text
Request comes in
   ↓
Resource Policy check
   ↓
IF allowed → Authentication (IAM/Cognito/etc.)
   ↓
IF denied → Block immediately
```

👉 So it runs **before authentication**

---

# 💡 Example Use Cases

✔️ Allow only company IPs  
✔️ Allow only specific AWS accounts  
✔️ Restrict to internal VPC (private APIs)

---

# 🧾 Example (IP Restriction)

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "execute-api:Invoke",
  "Resource": "arn:aws:execute-api:region:account-id:api-id/*",
  "Condition": {
    "IpAddress": {
      "aws:SourceIp": "203.0.113.0/24"
    }
  }
}
```

👉 Only this IP range can access the API

---

# 🆚 Resource Policy vs Auth

|Feature|Resource Policy|Auth (IAM/Cognito)|
|---|---|---|
|Purpose|Who can reach API|Who you are|
|Level|Network/account|User identity|
|Runs|First|After|

---

# 🎯 One-Line Summary

👉 **Resource Policy = First security filter (network-level access control)**



# 🧠 API Gateway – Additional Features (Quick Summary)

### 1. 🔄 API Versioning

- Create multiple versions of APIs (v1, v2)
- Avoid breaking existing clients
- Test new versions before making them live

### 2. 🏷️ Stages (Environments)

- Examples: `dev`, `test`, `prod`
- Each stage can have:
    - different throttling limits
    - logging settings
- Helps manage environments cleanly


### 3. 🔑 API Keys

- Unique key per client
    
- Used for:
    
    - **Tracking usage**
        
    - **Applying throttling limits**
        
- Not strong security (just identification + control)
    

---

### 4. ⚡ Caching

- API Gateway can cache responses
    
- Benefits:
    
    - Faster responses
        
    - Reduced backend load
        

---

### 5. 🔀 Request/Response Transformation

- Modify data between client ↔ backend
    
- Example:
    
    - Client sends JSON → backend expects XML
        
- Useful for decoupling client & backend formats
    

---

### 6. 🛡️ AWS WAF Integration

- Protect APIs from attacks:
    
    - SQL injection
        
    - XSS
        
    - bots
        
- Works at **Layer 7 (HTTP level)**
    

---

👉 API Gateway also provides **versioning, environments, usage control, caching, transformation, and security (WAF)** on top of basic routing.
