
# 🧱 Row-Based Storage

### Table:

CustomerID | Name  | City | Age  
--------------------------------  
C1         | Alice | NY   | 25  
C2         | Bob   | LA   | 30

### Stored like:

Row1 → [C1, Alice, NY, 25]  
Row2 → [C2, Bob, LA, 30]

👉 Data stored **row by row**

---

# 📊 Column-Based Storage

### Same Table:

CustomerID | Name  | City | Age

### Stored like:

CustomerID → [C1, C2]  
Name       → [Alice, Bob]  
City       → [NY, LA]  
Age        → [25, 30]

👉 Data stored **column by column**

### 🧱 Row-Based → Use When:

- You need **full records**
- Frequent **inserts/updates**
- Example:  
    👉 User profiles, orders, transactions (DynamoDB, MySQL)

---

### 📊 Column-Based → Use When:

- You need **few columns over many rows**
- Heavy **analytics / aggregation**
- Example:  
    👉 Reports, dashboards, SUM/AVG queries (Redshift, BigQuery)

---

### ⚡ One-liner:

Row → transactional apps  
Column → analytics/reporting

# 🧠 1. What is AWS Glue (In One Line)

👉 **AWS Glue = Serverless ETL + Data Catalog**

It:

- Extracts data
- Transforms it
- Loads it
- AND manages metadata (schema)

# 🏗️ 2. Core Components of AWS Glue

Think of Glue as 4 main building blocks:

## 🧩 1. Data Sources

Glue can connect to **70+ sources**:

- S3 (most common)
- RDS / Aurora
- DynamoDB
- On-prem databases
- External sources (MongoDB, BigQuery, etc.)

👉 Key idea:

> Glue doesn’t care where data lives—as long as it can connect.

Glue Just need connection to the DB.


## 🕷️ 2. Glue Crawlers (Schema Discovery)

This is 🔥 important. Once Glue connected to the DB - It does the schema discovery. It understands the structure of data and build the data catalog using default or customised classifier.


### What it does:
- Scans your data
- Infers schema (columns, types, structure). It understands the structure of data.
- Stores metadata

### Example:

CSV file:
```csv
user_id,name,age
1,Alice,25
```

Crawler creates:

```json
{
  "columns": [
    {"name": "user_id", "type": "int"},
    {"name": "name", "type": "string"},
    {"name": "age", "type": "int"}
  ]
}
```

## 📚 3. Glue Data Catalog

👉 This is the **central metadata repository**

- Stores table definitions
- Used by:
    - Athena
    - Redshift Spectrum
    - EMR
    - Glue itself
💡 Think:

> “Hive Metastore managed by AWS”

## 🟢 Step 1: Data in S3 (Raw Logs)

s3://my-bucket/logs/  
    file1.json  
    file2.json

Example JSON:

{"user_id": 2, "status": 500}

## 🟡 Step 2: Glue Crawler Runs

👉 The crawler:

- Scans S3
- Detects schema
- Creates a **table in Glue Data Catalog**

### Result:

Table created:

Database: my_db  
Table: logs_table  
Location: s3://my-bucket/logs/

Schema:

user_id → int  
status → int

## 🔵 Step 3: Athena Uses Glue Catalog

Now here's the key point 👇

👉 Athena does NOT scan S3 blindly  
👉 It uses **Glue Catalog as schema**

### You can now run:

SELECT * FROM logs_table WHERE status = 200;

### What happens internally:

Athena → reads Glue Catalog → knows schema + S3 path  
       → scans S3 files → executes query

✔️ No ETL needed  
✔️ No data movement


## ⚙️ 4. Glue Jobs (ETL Execution)

This is where actual work happens. Based on data catlog - transformation logic works.

### You define:

- Source
- Transform logic
- Target

### Supported engines (logic)

- Apache Spark (most common)
- Python (shell jobs)
- Ray (for distributed Python)

# 🚨 5. The BIG Problem (Without Bookmarks)

Let’s say:

- Day 1 → process 1GB data
    
- Day 2 → new 100MB arrives
    

### ❌ Without bookmarks:

```text

```

Problems:

- Slow
    
- Expensive 💸
    
- Duplicate data ❗

# ✅ 6. Glue Job Bookmarks (CRITICAL CONCEPT)

👉 **Bookmarks = Incremental processing state**

They track:

- Processed files
    
- Timestamps
    
- Partitions
    
- Job state
    

---

## 🧠 How It Works

```text
Run 1 → process files A, B
Run 2 → only process new file C
```

---

## ⚙️ What It Stores

- S3 file paths
    
- Last processed timestamp
    
- Partition values
    
- Job success/failure state
    

---

## 🔥 Behavior in Edge Cases

### If previous job FAILED:

👉 Glue will:

- Retry unprocessed data
    

### If bookmark DISABLED:

👉 Glue will:

- Reprocess everything
    

---

# ⚖️ 7. When to Use vs NOT Use Bookmarks

## ✅ Use Bookmarks (Most Cases)

- Incremental data (logs, events)
    
- Streaming-like ingestion
    
- Cost optimization
    

---

## ❌ Don’t Use Bookmarks

When:

- You changed transformation logic
    
- You want to **reprocess historical data**
    

👉 Example:

> “We fixed a bug in transformation → re-run everything”

# 🧠 1. What is a Glue Classifier?

👉 A **classifier** tells Glue:

> “How should I interpret this data format?”

## By default, Glue has built-in classifiers:

- CSV
- JSON
    
- Parquet
    
- Avro
    

✔️ Works most of the time  
❗ Fails when data is **non-standard**

---

# 🚨 2. When Do You Need a Custom Classifier?

Use it when Glue crawler:

- ❌ Detects wrong schema
    
- ❌ Merges columns incorrectly
    
- ❌ Fails to parse logs
    
- ❌ Cannot identify format
    

---

## 🔥 Common Real Cases

### Example 1: Custom log format

```text
2026-04-01|INFO|user123|login_success
```

👉 Not CSV (delimiter is `|`)

---

### Example 2: CSV without header

```text
1001,501,2026-04-01
```

👉 Glue doesn’t know column names

---

### Example 3: Nested JSON weird structure

👉 Glue may flatten incorrectly

---

# 🧩 3. Types of Custom Classifiers

Glue supports:

---

## 🟢 1. Grok Classifier (Most Powerful)

👉 Used for:

- Logs
    
- Semi-structured text
    

---

### Example:

Input:

```text
2026-04-01|INFO|user123|login_success
```

Grok pattern:

```text
%{TIMESTAMP_ISO8601:timestamp}\|%{WORD:level}\|%{WORD:user}\|%{WORD:event}
```

---

## 🔵 2. CSV Classifier

👉 Customize:

- Delimiter
    
- Header presence
    
- Quote symbols
    

---

### Example:

- Delimiter: `|`
    
- Header: No
    

---

## 🟣 3. JSON Classifier

👉 For:

- Custom JSON structures
    
- Multi-line JSON
    

---

## 🟡 4. XML Classifier

👉 For XML files

---

# 🔒 2. Encryption IN TRANSIT (Automatic)

👉 Glue uses **TLS (HTTPS)**

### What gets encrypted:

- Glue ↔ S3
    
- Glue ↔ RDS
    
- Glue ↔ Redshift
    
- Glue ↔ any data source
    

---

## 💡 Key Point

> ✔️ You don’t configure this manually  
> ✔️ It’s **enabled by default**

# 🧊 3. Encryption AT REST (Where things get interesting)

Glue can encrypt multiple components:

---

## 🟢 1. Glue Data Catalog Encryption

👉 Metadata (tables, schemas) stored securely

### Uses:

- **AWS KMS**
    

---

### Enable it:

In Glue:  
👉 **Settings → Data Catalog encryption**

Choose:

- KMS key
    

---

## 🔵 2. CloudWatch Logs Encryption

Glue jobs + crawlers generate logs

👉 These logs can be encrypted using:

- KMS
    

---

### Why important?

Logs may contain:

- Data samples
    
- Errors with sensitive info
    

---

## 🟣 3. Job Bookmarks Encryption

Remember:

- Bookmarks store processed state
    

👉 These are also encrypted via KMS

---

## 🟡 4. S3 Target Data Encryption

When Glue writes to S3:

---

### Option A: SSE-S3 (Simple)

```text
AES-256 encryption (AWS managed)
```

✔️ Easy  
✔️ Default

---

### Option B: SSE-KMS (Advanced)

```text
AWS KMS key used
```

✔️ More control  
✔️ Audit + key rotation

---

### Example in Glue Job:

```python
df.write \
  .option("compression", "snappy") \
  .option("path", "s3://bucket/processed/") \
  .save()
```

👉 Encryption is controlled by:

- S3 bucket settings OR
    
- Glue job configuration
    

---

# 🔥 4. Where KMS Fits In

Used for:

- Data Catalog

# ⚠️ 6. Important Gotcha (VERY COMMON)

If using **SSE-KMS on S3**:

👉 Glue role MUST have:

```json
{
  "Action": [
    "kms:Decrypt",
    "kms:Encrypt",
    "kms:GenerateDataKey"
  ],
  "Effect": "Allow",
  "Resource": "*"
}
```

---

## ❗ Without this:

- Jobs fail
    
- Crawler fails
    
- You’ll see “Access Denied” errors
